第一章 · 计算机网络

第 1 课 · 网络为什么要分层

要解决的问题：一台电脑的数据要跑到几千公里外的另一台电脑，中间经过几十台设备，而这些设备是不同厂商造的、代码各写各的。它们凭什么能配合？

答案：分层。每一层只解决自己的一个问题，对上提供接口，对下隐藏细节。

类比寄快递：你只写收件地址、把包裹交给快递员，不需要知道快递员骑电动车还是开货车、走高速还是国道、飞机几点起飞。但取件、分拣、运输、派件每一环都真的发生了，而且每一环只干自己那一环的事。

层干什么快递里对应谁
应用层数据是什么内容、什么格式你写的地址和包裹里的东西
传输层保证数据不丢、不乱序快递公司承诺"必达、按顺序"
网络层决定走哪条路、送到哪台机器分拣中心按城市规划路线
网络接口层在真实的线缆 / WiFi 上把信号发出去货车、飞机、电动车
关键结论：分层 = 每一层只解决自己的一个问题，对上提供接口，对下隐藏细节。八股里绝大多数题，本质都在问"某一层具体干了什么"。
第 2 课 · 封装与解封装

先认四个外号。同一份数据在不同层里名字不同，数据本身没变，是外面套的壳变了：

层这份数据叫什么
应用层报文（message）
传输层段（segment，TCP） / 数据报（datagram，UDP）
网络层包、也叫分组（packet）
数据链路层帧（frame）
物理层比特（bit），就是 0 和 1

头（header）：每层在自己这层数据外面贴的一张小纸条，只写"这一层需要知道的信息"。

发送方向下走，一层套一层壳（封装）：

层往外套了什么套完叫什么
应用层请求内容 + 格式说明等HTTP 报文
传输层TCP 头：源端口、目标端口、序号…TCP 段
网络层IP 头：源 IP、目标 IPIP 包
数据链路层帧头帧尾：源 MAC、目标 MAC帧

接收方反着来，一层撕一个壳（解封装），最后把内容交给真正要它的程序。

为什么非要分这么细：因为每一层只看懂自己那层的小纸条。路由器不需要知道你请求里的内容，它只看 IP 头里"目标 IP 是谁"；你的程序也不需要知道信号是 WiFi 还是网线。
关键结论：封装 = 每层往外面套一层自己的信封；解封装 = 对面一层层撕开。
第 3 课 · OSI 七层是什么

OSI 三个字母：Open（开放的）+ Systems（系统）+ Interconnection（互相连接，inter = 相互，connection = 连接）= 开放系统互联。

它是一个参考模型（reference model，reference = 参考，model = 模型），说白了就是一张"标准答案式"的表格，由国际标准化组织（ISO）制定，规定两台电脑通信该分成几层、每层负责什么。

注意"参考"两个字：它不是真实运行的东西，是描述用的框架。就像营养学会的"膳食宝塔"——你吃饭并不真的按宝塔吃，但宝塔能帮你理解该吃什么。

层的英文是 layer，就是一层一层的意思。从下往上数：

层号中文英文（拆词）它管的事
7应用层Application（apply = 应用）你具体要干什么：开网页、发邮件、传文件
6表示层Presentation（present = 呈现、表示）数据的格式：翻译、压缩、加密解密
5会话层Session（一次交谈、一次会话）管理这次对话的开始、保持、结束
4传输层Transport（运输）数据可不可靠：丢没丢、顺序对不对
3网络层Network（网络）数据走哪条路、送到哪个地址
2数据链路层Data Link（data = 数据，link = 链接）相邻两台设备之间怎么把数据递过去
1物理层Physical（物理的）把 0 和 1 变成真实的电信号、光、无线电波

换成寄信理解：

层现实里对应的事
7 应用层"我要寄的是一份合同"——这是目的
6 表示层合同是中文的，得翻译成英文、再装进档案袋封好
5 会话层打电话约定："我这周寄给你，你收到回我一声"
4 传输层选顺丰：必达、丢件赔、按顺序送到
3 网络层看地址，决定走郑州还是走武汉
2 数据链路层你家 → 快递柜 → 网点，一段一段往下交
1 物理层货车、铁路、飞机——真正在动的东西

怎么背（八股要背顺序）：

物 · 链 · 网 · 传 · 会 · 表 · 应
关键结论：OSI = 把网络通信分成七层的理论标准表格，从下到上是物、链、网、传、会、表、应。上面几层管"内容对不对"，下面几层管"怎么把东西送过去"。
第 4 课 · OSI 七层 vs TCP/IP 四层 / 五层

先拆两个英文词：

缩写英文拆开
TCPTransmission Control Protocoltransmission = 传输，control = 控制，protocol = 协议 → 传输控制协议
IPInternet Protocolinternet = 互联网，protocol = 协议 → 网际协议

协议（protocol）= 双方事先约定好的一套规则。像两个人打电话得先约定说中文还是英文、谁先说；电脑之间也一样，"怎么开头、怎么回应、发错了怎么办"这些约定就叫协议。

真实世界用的是 TCP/IP 模型，只有四层。对应关系：

OSI 七层TCP/IP 四层变化
7 应用层 + 6 表示层 + 5 会话层应用层三层合并成一层
4 传输层传输层原样保留
3 网络层网络层原样保留
2 数据链路层 + 1 物理层网络接口层两层合并成一层

记忆：上面三层合一，中间两层不动，下面两层合一。四层自上而下 = 应、传、网、接。

为什么合并？理论 vs 现实的差别：

  • OSI 是先把模型想好再去写协议，想得很细致所以分了七层，但太复杂、实现太慢，没推广开。
  • TCP/IP 是先做出来（美国军方的 ARPANET），做完再回头总结分层，只求能跑通，不实用的就合并。

五层模型不是第三种东西，是教学折中版：上面按 TCP/IP 合并，下面按 OSI 不合并。

五层：应用层 · 传输层 · 网络层 · 数据链路层 · 物理层
面试问"OSI 和 TCP/IP 的区别"，答题三要点：① 层数不同（7 层 vs 4 层）；② 一个是理论模型，一个是事实标准；③ 一个先有模型后有协议，一个反过来先有实现后有模型。
第 5 课 · 数据单位与网络设备（哪个盒子在第几层）

每一层的数据有自己的名字，从上层到下层依次是：

报文 → 段 → 包 → 帧 → 比特
层数据单位英文（拆词）
应用层报文message（消息）
传输层段 / 数据报segment（segment = 一段） / datagram（data + gram = 数据 + 写下来的东西）
网络层包、分组packet（packet = 一小包）
数据链路层帧frame（frame = 框、框架）
物理层比特bit（binary digit 二进制数字的缩写）

三个"盒子"，各自站在不同的层上：

设备英文（拆词）在哪一层它认什么
集线器 / 中继器Hub（轮毂、中心）/ Repeater（repeat = 重复 + er = 重复干这事的东西）物理层什么都不认，只把信号放大、往所有口转发
交换机 / 网桥Switch（开关、切换）/ Bridge（桥）数据链路层认 MAC 地址（Media Access Control，介质访问控制），能精确送到某一台机器
路由器Router（route = 路线 + er = 干这事的东西）网络层认 IP 地址，负责在不同网络之间找路
关键感觉：设备越往上，认的东西越"高级"——集线器不认地址 → 交换机认 MAC → 路由器认 IP。
高频面试题："路由器和交换机有什么区别？"
① 工作层次不同：路由器在网络层，交换机在数据链路层；
② 依据不同：路由器按 IP 地址转发，交换机按 MAC 地址转发；
③ 范围不同：交换机管一个局域网内部，路由器负责把数据送出这个网、送到别的网。
第 6 课 · 局域网 / 广域网 / 互联网（LAN / WAN / Internet）

"局域网"三个字拆开就是它的全部意思：局部的、一定区域内的网络。

中文英文拆词
局域网LAN = Local Area Networklocal = 本地的，area = 区域，network = 网络 → 本地区域的网络
广域网WAN = Wide Area Networkwide = 广阔的 → 大范围的网络
互联网Internetinter = 相互 + net = 网 → "网的网"，把所有网络连起来的那张网

用小区和城市道路类比：

  • 局域网 = 一个小区内部的道路。谁住哪栋楼、门牌号多少，物业自己清楚、自己管。
  • 广域网 = 城市之间的高速公路。连接不同城市，归国家/运营商管。
  • 互联网 = 把所有城市、所有小区都连起来的那张总路网。

现实里对应：

范围例子属于
你家手机、电脑、电视连同一个 WiFi一个局域网（你家路由器自己管）
一间机房 / 一个公司几十台电脑插在同一个交换机上一个局域网
一个城市联通在这个城市的骨干网络广域网（运营商管）
全世界访问别的国家的网站互联网

一个自查小技巧：同一个局域网里的设备，IP 地址前面的部分通常一样（比如都是 192.168.1.x），因为它们共用同一个"网段"。这件事讲 IP 地址时再细说。

关键结论：局域网 = 一个"自己说了算"的小网络，范围小、自己管；广域网 = 把很多局域网连起来的大网络，归运营商管；互联网 = 所有网络连起来的网。
为什么这个概念重要（回头看第 5 课）：因为 MAC 地址只在一个局域网内部有效，出了这个网就没人认；跨局域网要靠 IP 地址。所以局域网内部用交换机（认 MAC）就够了，要出这个网就必须有路由器（认 IP）。三个盒子的分工就是这么来的。
第 7 课 · 协议地图（每层都有哪些协议）
破解一切缩写的方法：协议名全都是"英文全称的首字母缩写"。看到不认识的缩写，先去找它的全称，全称看懂了，它是干什么的也就懂了。
层协议英文全称拆词干什么（一句话）
应用层HTTPHyperText Transfer Protocol：hyper = 超，text = 文本，transfer = 传输 → 超文本传输协议传网页
HTTPSHTTP + Secure（安全的）加密版的 HTTP
DNSDomain Name System：domain = 域名，name = 名字，system = 系统 → 域名系统把网址（www.xxx.com）翻译成 IP 地址
传输层TCPTransmission Control Protocol → 传输控制协议可靠：不丢、不乱序（像打电话）
UDPUser Datagram Protocol：user = 用户，datagram = 数据报 → 用户数据报协议快但不可靠：不管丢没丢（像寄明信片）
网络层IPInternet Protocol → 网际协议给数据写上源 IP、目标 IP，负责找路
ICMPInternet Control Message Protocol：control = 控制，message = 消息 → 网际控制报文协议报告"网络出问题了"，ping 命令用的就是它
ARPAddress Resolution Protocol：address = 地址，resolution = 解析 → 地址解析协议知道对方的 IP，问出对方的 MAC 地址
数据链路层Ethernet（以太网）不是缩写，就是个名字最常见的局域网技术，管"相邻设备之间怎么传帧"

另外 FTP（File Transfer Protocol，传文件）、SMTP（Simple Mail Transfer Protocol，发邮件）、SSH（Secure Shell，远程登录）也都是应用层的协议，先混个脸熟，不用现在背。

这一课只要"地图"，不要"细节"。11 个名字里真正需要现在就记住的只有三个：TCP、UDP、HTTP。其余的先做到"看到能想起来它在哪一层"就够了。
关键结论：协议 = 某一层上的规则；名字都是英文全称的首字母；想知道一个协议干什么，先把它拆成全称。
第 8 课 · TCP 与 UDP 的区别（八股第一高频）

TCP 和 UDP 是同一层（传输层）上的两个选择。它们解决的是同一个问题——"数据怎么从我的程序送到对面的程序"，只是取向不同：一个要可靠，一个要快。

TCP 像打电话 · UDP 像寄明信片
  • TCP 像打电话：先拨号、对方接起来（建立连接），说的每句话对方都会"嗯"一声（确认），没听清就再说一遍（重传），而且听得出来顺序（哪句先说的）。
  • UDP 像寄明信片：写好直接扔邮筒，不管对方收没收到、不管会不会比另一张晚到。但快、省事。

TCP 的"可靠"不是白来的，是靠下面这几件事一点点换来的（每一项以后都会单独讲）：

  • 建立连接：通信前先打招呼确认双方都在（这就是"三次握手"）。
  • 确认（ACK）：收到就回一句"我收到了"。
  • 超时重传：一定时间没等到确认，就再发一次。
  • 排序：给每段编号，对方按编号拼回去，所以不会乱序。
  • 流量控制 / 拥塞控制：对方处理不过来、或者网络堵了，就发慢一点。

UDP 这几件事一件都不做——所以它又快又轻，但丢了就是丢了。

八股标准对比表：

对比项TCPUDP
连接面向连接：先建立连接再传数据无连接：直接发
可靠性可靠：确认、重传、不丢不乱序不可靠：丢包不负责
速度 / 开销慢，开销大快，开销小
数据形式字节流：像水管里的水，连成一片、没有边界数据报：像一个个包裹，有边界，发一个收一个
头部大小最少 20 字节8 字节
通信方式只能一对一一对一、一对多、多对多都行（支持广播 / 组播）
典型场景网页、文件下载、邮件——不能错的地方直播、视频通话、网络游戏、DNS——慢一点没关系、丢了就丢了的地方
为什么直播用 UDP？因为直播里"这一帧画面"晚到了，重传回来也没用了——用户要的是"现在这一秒的画面"，不是"三秒前丢的那一帧"。宁可糊一下，也不能卡。这就是"取向不同"的意思。
关键结论：TCP 用"确认 + 重传 + 排序"这些额外动作换来可靠性，代价是慢和开销大；UDP 什么都不管，所以快。选哪个，取决于你的场景怕不怕丢数据。
第 9 课 · TCP 三次握手

TCP 是"面向连接"的，所以正式传数据之前，双方要先打个招呼确认彼此都在、都能收发。这个打招呼的过程就叫握手（handshake）。因为一共来回三次，所以叫三次握手。

先认几个词：

词全称 / 拆词意思
SYNSynchronize（同步）一个标志位，值为 1 时表示"我想建立连接 / 我在跟你对齐序号"
ACKAcknowledgement（确认）一个标志位，值为 1 时表示"我确认收到了"
seqsequence number（序号）我这一方要发的数据的起始编号
ackacknowledgement number（确认号）"我期望下一次收到第几号"——表示这个号之前的全都收到了

三次握手的过程：

第几步方向发的东西人话
①客户端 → 服务器SYN=1，seq=x"我想跟你通信，我的起始序号是 x"
②服务器 → 客户端SYN=1，ACK=1，seq=y，ack=x+1"行，我也想跟你通信，我的起始序号是 y，你那个 x 我收到了"
③客户端 → 服务器ACK=1，seq=x+1，ack=y+1"收到你的 y 了，开始吧"

三步走完，双方都进入 ESTABLISHED（已建立）状态，才开始真正传数据。

为什么 ack 要写成 x+1 而不是 x？因为确认号的含义是"我期望下一次收到第几号"。写 x+1，等于说"x 及 x 之前的所有数据我全收到了，下一次请从 x+1 开始发"。这是 TCP 表达"累计确认"的方式。
喂，能听见吗 → 能听见，你呢 → 能听见，那我们说吧

为什么必须是三次，不能两次？两个理由，都要记住：

  1. 只有三次，双方才能都确认"自己发得出、对方收得到"。第一次之后服务器知道"客户端能发、我能收"；第二次之后客户端知道"服务器能发、我能收"；但此时服务器还不知道客户端能不能收到自己的话——必须等第三次。两次握完，服务器是"单方面相信"的。
  2. 防止一个"过期的旧连接请求"骗到服务器。如果客户端很早发的一个 SYN 卡在网络上，很久之后才突然到达服务器：两次握手的话，服务器一收到就认为连接建好了，白白分配资源等着，而客户端根本不认这个连接。有了第三次，客户端会拒绝这个旧请求，服务器也就不会白白等待。
关键结论：三次握手是为了让双方都确认彼此的收发能力正常，同时挡掉迟到的旧请求。四次没必要——第三次已经把该确认的确认完了。
第 10 课 · TCP 四次挥手

连接用完了要断开，断开前也要打招呼，这个过程叫挥手。因为来回四次，所以叫四次挥手。

先认两个词：

词拆词意思
FINFinish（结束）标志位，=1 表示"我没有数据要发了，想断开"
MSLMaximum Segment Lifetime报文在网络里能存活的最长时间

四次挥手的过程（假设客户端主动关闭）：

第几步方向发的东西人话
①客户端 → 服务器FIN=1，seq=u"我没数据要发了，想关"（客户端进入 FIN_WAIT_1）
②服务器 → 客户端ACK=1，ack=u+1"知道了"（服务器进入 CLOSE_WAIT，客户端进入 FIN_WAIT_2）
③服务器 → 客户端FIN=1，seq=w"我这边也说完了，可以关了"（服务器进入 LAST_ACK）
④客户端 → 服务器ACK=1，ack=w+1"知道了"（客户端进入 TIME_WAIT，等待 2MSL 后关闭；服务器收到后进入 CLOSED）
为什么挥手四次、握手只有三次？因为 TCP 是全双工的——两个方向可以同时传数据，所以两个方向的关闭是各自独立的事。收到对方的 FIN，只说明"他不发了"，不代表"我也不发了"——服务器可能还有数据没发完。所以它先把 ACK 单独回一个（第②步），等自己真发完了再发 FIN（第③步）。
而握手时，双方都还没有遗留数据要发，所以服务器的 SYN 和 ACK 可以合并成一个包（SYN + ACK），少了一次。

为什么客户端最后还要等 2MSL（TIME_WAIT 状态）？两个原因：

  1. 保证最后那个 ACK 能送到。如果第④步的 ACK 在路上丢了，服务器会以为客户端没收到 FIN，于是超时重发 FIN。此时客户端还在 TIME_WAIT，就能再回一个 ACK。如果客户端发完直接关掉走人，服务器就永远等不到 ACK，无法正常关闭。
  2. 让这条连接的旧报文彻底消失。等 2MSL，本次连接残留在网络里的所有报文都会过期死掉，这样就不会串到下一个刚建立、恰好用了相同端口的新连接里去。
关键结论：挥手四次是因为全双工下"两个方向要分别关"，所以 ACK 和 FIN 得分成两次发；TIME_WAIT 等 2MSL 是为了保证最后一个 ACK 能补发、并让旧报文死干净。
第 11 课 · HTTP 请求与响应

HTTP = HyperText Transfer Protocol，超文本传输协议，应用层协议。它就是浏览器和服务器之间"我要东西 / 给你东西"的一套规矩。

它的工作方式是一问一答：客户端发一个请求，服务器回一个响应。服务器不会主动找你说话。

它跑在谁身上：HTTP/1.1 和 HTTP/2 都建立在 TCP 之上（所以前面讲的握手、挥手都是它的地基）；HTTP/3 改用了 UDP（底层是一套叫 QUIC 的东西）。这是近年的新考点，先知道有这回事。

请求报文长这样（三部分）：

GET /index.html HTTP/1.1          ← ① 请求行：方法 + 路径 + 版本
Host: www.example.com              ← ② 请求头（一堆 key: value）
User-Agent: Chrome/120
Accept: text/html

                                   ← ③ 空行之后是请求体（GET 一般没有体）

响应报文也长这样（三部分）：

HTTP/1.1 200 OK                    ← ① 状态行：版本 + 状态码 + 说明
Content-Type: text/html            ← ② 响应头
Content-Length: 1234

<html>...</html>                  ← ③ 空行之后是响应体（真正的内容）

常见请求方法：

方法意思备注
GET获取资源最常用。参数跟在网址后面（?a=1&b=2）
POST提交数据参数放在请求体里
PUT全量更新把整个资源替换掉
PATCH局部更新只改一部分
DELETE删除资源—
HEAD只要响应头，不要响应体用来探路、看文件多大

GET 和 POST 的区别（高频）：

对比项GETPOST
语义获取提交
参数位置拼在 URL 后面，人人可见放在请求体里
能否缓存 / 收藏成书签能一般不能
幂等性幂等（做一次和做十次结果一样）不幂等（提交十次就多十条数据）
数据量受 URL 长度限制，传不了大的能传很大（HTTP 协议本身对两者都没设上限，限制来自浏览器和服务器）

状态码：看第一位数字就知道是哪一类。

开头类别含义
1xx信息收到请求了，还在处理
2xx成功办好了

4xx客户端错误你的请求有问题

状态码意思

关键结论：HTTP 是"一问一答"的应用层协议，报文分行 + 头 + 体三部分；方法决定"要干什么"；状态码看第一位就知道是成功、重定向，还是你错、还是服务器错。
